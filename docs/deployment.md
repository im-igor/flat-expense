# Развёртывание на виртуальной машине Yandex Cloud

## Первая установка

Для MVP достаточно начать с Ubuntu 24.04 LTS, 2 vCPU, 2–4 ГБ памяти и SSD от 20 ГБ. Это стартовая конфигурация без локальной языковой модели; фактические требования зависят от объёма данных. Облачные ресурсы и их оплата в репозитории не настроены автоматически.

1. Создайте VM, добавьте SSH-ключ. Разрешите входящий SSH только с нужных адресов. Входящие 8000/5432 и публичный HTTP боту не нужны: он сам опрашивает Telegram.
2. Установите Docker Engine и Compose plugin по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/), а также Git и Python 3. Пользователь запуска должен иметь доступ к Docker; такой доступ даёт административные полномочия на VM.
3. Клонируйте репозиторий, выполните `scripts/configure.py` и запуск из README. Не переносите токен через аргументы команд, историю shell или сообщения.
4. Проверьте `docker compose ps` и ответ `/health`. Если переносите историю, сначала выполните импорт из README: даже удалённые тестовые записи означают, что учёт уже начат, поэтому проверять ввод нужно после импорта.
5. Создайте тестовую оплату через бота, проверьте её в сводке и удалите через карточку. Сделайте резервную копию и проверьте восстановление. Затем запишите реальный расход и отдельный будущий план.

PostgreSQL хранит данные в именованном Docker volume. `docker compose down` сохраняет данные; **`docker compose down -v` удаляет их**. API слушает только loopback VM. Домен и сертификат для Telegram long polling не требуются.

Доступ к API с локального компьютера при необходимости — через SSH-туннель:

```bash
ssh -L 8000:127.0.0.1:8000 USER@VM_ADDRESS
```

API использует служебный Bearer-токен и заголовок `X-Telegram-User-Id`. Это доверие между сервисами, а не пользовательская веб-авторизация: владелец служебного токена может действовать от любого разрешённого ID. Не публикуйте API в интернет и не встраивайте токен в браузерный клиент. `/openapi.json` тоже требует Bearer-токен.

## Локальный ИИ для Telegram

Модель работает в контейнере `expense-ai` без опубликованного порта. API сопоставляет текст текущего расхода с названиями и описаниями категорий владельца через локальные эмбеддинги; числовые реквизиты убираются из поискового текста. Суммы и даты извлекаются проверяемыми правилами, не генерируются моделью. Смысловое сходство дополняется совпадением терминов справочника; при низком сходстве или близких результатах бот просит выбрать категорию вручную. История расходов, Telegram ID, токены и БД модели недоступны. Модель создаёт только предложение: оплату сохраняет существующий сервис после явного подтверждения карточки.

```bash
docker compose --profile ai up --no-deps -d expense-ai
docker compose exec expense-ai ollama pull embeddinggemma:300m-qat-q8_0
```

В защищённой `.env` задайте `EXPENSE_AI_ENABLED=true`, `EXPENSE_AI_MODEL=embeddinggemma:300m-qat-q8_0`, `EXPENSE_AI_TIMEOUT=90`. После обновления образа приложения:

```bash
docker compose --profile ai --profile bot up --no-build --pull never -d
docker compose run --rm --no-deps \
  -v "$PWD/scripts/evaluate-expense-ai.py:/tmp/evaluate-expense-ai.py:ro" \
  api python /tmp/evaluate-expense-ai.py
```

Скрипт оценки использует синтетические примеры и не обращается к БД. Проверяет числа, даты, категории, отсутствие суммы, аванс, будущие покупки и несколько оплат. Набор небольшой: успех на нём не гарантирует правильную классификацию произвольного текста. Приёмка различает автоматический выбор и безопасный запрос категории у пользователя. Перед сохранением всегда проверяйте карточку.

Контейнер модели ограничен 1,5 CPU, 1000 МБ RAM и 1300 МБ RAM+swap. Для ВМ с 2 ГБ памяти начинайте с компактной модели и проверьте запас памяти вместе с API и PostgreSQL. Параллельность inference ограничена одним запросом. Не открывайте порт 11434 наружу. Для загрузки весов нужен исходящий доступ к registry Ollama; сами сообщения обрабатываются локально.

При таймауте или невалидном ответе модели расходы не создаются, доступен `/expense`. `/start` восстанавливает текущий черновик, `/cancel` очищает его. Замена модели не требует миграции БД. Для отключения ИИ задайте `EXPENSE_AI_ENABLED=false` и пересоздайте API; ручной бот продолжит работать.

## Резервные копии

```bash
bash scripts/backup.sh
bash scripts/verify-backup.sh backups/flat-ДАТА.dump
```

Первый скрипт создаёт приватный архив PostgreSQL, второй восстанавливает его **в новую временную базу**, читает версию схемы и таблицы, затем удаляет только эту временную базу. Проверка не перезаписывает рабочую БД. Скрипты предполагают имена базы и пользователя `flat` из Compose.

Настройте ежедневное выполнение `backup.sh` (cron/systemd timer) и копирование архивов за пределы VM, например в приватный Yandex Object Storage с шифрованием и политикой хранения. **Автоматическое расписание, S3-выгрузка, срок хранения и оповещения пока не настроены.** Архив на том же диске не защищает от потери VM. Секрет `.env` храните отдельно в защищённом хранилище; DB-архив его не содержит.

Для аварийного восстановления создайте новую установку с пустой базой, запустите только `db`, затем восстановите архив до запуска миграций/API. Не выполняйте это в существующей рабочей базе:

```bash
docker compose up -d db
# Дождитесь healthy в docker compose ps.
docker compose exec -T db pg_restore -U flat -d flat \
  --exit-on-error --no-owner < /secure/path/flat.dump
docker compose --profile bot up --build -d
```

Восстанавливайте сначала на той версии кода, которая соответствует архиву. При новой версии приложения запускаются последующие миграции. Для смены Telegram-бота учтите, что сохранённый курсор и ключи повторных сообщений относятся к прежнему боту; MVP рассчитан на один неизменный бот на установку, такая смена требует отдельной миграции.

## Обновление

Сначала резервная копия и её проверка. Затем `git pull --ff-only` и `docker compose --profile bot up --build -d`. Миграции запускаются перед API. Для отката к старому коду заранее проверьте совместимость его схемы; возврат коммита сам по себе не откатывает базу. Сохраните используемый commit ID рядом с копией.

Для диагностики используйте `docker compose ps` и `docker compose logs --tail=100 api bot migrate`. Не публикуйте `.env`, вывод `docker compose config` или инспекцию окружения контейнеров: они могут содержать секреты. Не удаляйте webhook старого бота без запланированного переключения. Не запускайте два polling-процесса с одним Telegram-токеном.

## Границы текущей проверки

Локально проверены расчёты, диалоги через API, импорт, миграции PostgreSQL 17 и восстановление архива. Реальная переписка с Telegram и облачная VM требуют отдельной проверки после подключения токена и сервера. Автоматическая сборка контейнеров описана в GitHub Actions; актуальный статус смотрите во вкладке Actions репозитория.

## Установка, если Docker Hub недоступен

Для Linux x86_64 готовые образы собираются в GitHub Actions и публикуются в [Releases](https://github.com/im-igor/flat-expense/releases). Комплект содержит приложение и PostgreSQL. Перед публикацией проверяются загрузка архива, запуск API без сборки/скачивания образов и восстановление резервной копии. Этот способ требует доступа VM к GitHub и его хранилищу файлов; для работы бота нужен доступ к Telegram.

После успешного завершения workflow `offline bundle` для текущей версии, из папки проекта:

```bash
git pull --ff-only
bash scripts/start-offline.sh
```

Скрипт проверит архитектуру, наличие `.env`, скачает архив для текущего коммита, проверит SHA-256, загрузит образы и запустит Compose с `--no-build --pull never`. Новые пароли не создаются, существующие настройки и volume базы сохраняются. Если `.env` ещё нет, сначала запустите `scripts/configure.py` из README. Не заменяйте команду запуска на `--build`: она снова потребует доступа к исходным реестрам.

Нужны свободное место для архива и образов (рекомендуется минимум 3 ГБ) и команды `curl`, `git`, `sha256sum`, Docker Compose. Временный архив удаляется при завершении скрипта. При ошибке 404 убедитесь, что workflow `offline bundle` именно для вашего коммита завершился успешно. Готовый комплект не исправляет сетевой доступ VM; при проблемах с GitHub или Telegram потребуется отдельная сетевая диагностика. Для другой архитектуры скрипт остановится до изменений.

## Telegram через HTTPS-релей

Если прямое соединение с Bot API недоступно, можно задать в `.env`:

```dotenv
TELEGRAM_API_ROOT=https://YOUR_TRUSTED_RELAY:9443
```

Это корневой адрес совместимого с Telegram Bot API HTTPS-релея, а не обычный HTTP/SOCKS-прокси. В адресе не должно быть пути `/bot...`, логина, пароля или параметров. Бот сам формирует пути API и файлов. Проверка TLS-сертификата остаётся включённой. Используйте только доверенный релей: он получает Telegram-токен как часть запросов API. Служебные запросы бота к локальному API приложения через него не идут.

На стороне релея может потребоваться добавить исходящий IP VM в разрешённый список. После изменения настройки пересоздайте контейнер бота командой `docker compose --profile bot up --no-build --pull never -d bot`. Для установок через готовые архивы сначала загрузите комплект новой версии. Успешный `/health` проверяет API и базу приложения, но не соединение с Telegram; его нужно проверить отдельно.

## Веб-интерфейс

### Прямой HTTP-доступ с паролем

Из корня проекта на VM запустите интерактивную настройку. Пароль не отображается, не попадает в историю shell и сохраняется только как scrypt-хеш:

```bash
python3 scripts/set-web-password.py --host SERVER_IP
docker compose up --no-build --pull never -d api
```

Скрипт публикует контейнер на порту 80 и разрешает указанный Host. Откройте `http://SERVER_IP/` и войдите с выбранным паролем. В облачной группе безопасности должен быть разрешён входящий TCP/80; PostgreSQL остаётся доступен только внутри Docker-сети. После шести неудачных входов с одного адреса действует пятиминутная блокировка.

HTTP не шифрует пароль, cookie и финансовые данные по пути между браузером и сервером. Этот режим подходит как временный; следующим шагом следует подключить домен и HTTPS. Не используйте пароль от других сервисов.

### Доступ через SSH

В `.env` на VM включите `WEB_ENABLED=true`, затем пересоздайте API без скачивания образов:

```bash
docker compose up --no-build --pull never -d api
```

Если разрешён один Telegram ID, веб-интерфейс автоматически использует тот же учёт. При нескольких ID укажите `WEB_OWNER_ID` из списка `ALLOWED_TELEGRAM_USER_IDS`. Доступ к Telegram для этого не нужен. Веб-интерфейс по умолчанию выключен.

На **своём компьютере**, оставляя терминал открытым:

```bash
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
  -L 127.0.0.1:8318:127.0.0.1:8000 USER@VM_ADDRESS
```

Откройте `http://127.0.0.1:8318/`. Эквивалентная команда из локальной копии проекта: `bash scripts/open-web.sh USER@VM_ADDRESS`. Это адрес туннеля на вашем компьютере; приложение и данные находятся на VM. Ctrl+C закрывает туннель. Если порт занят, выберите другой локальный порт.

Вход защищён вашим SSH-ключом/SSH-сеансом. Веб-интерфейс не запрашивает служебный API-токен и не передаёт его браузеру. Сервер выдаёт подписанную HttpOnly/SameSite-cookie на 8 часов; после истечения нужно обновить страницу. Для изменения данных проверяются Origin и дополнительный заголовок; доступны только loopback Host. Служебные Telegram endpoints по-прежнему требуют Bearer-токен.

В режиме SSH оставьте `WEB_PUBLIC=false`, `WEB_BIND_ADDRESS=127.0.0.1` и `WEB_PORT=8000`. Другие процессы и пользователи с доступом к локальному туннелю тоже могут открыть учёт.

В интерфейсе доступны обзор по месяцам, единый журнал оплат и будущих планов, график займа A–N, исправление/удаление/восстановление оплат, планы с согласованной ценой и несколькими платежами, архив, управление категориями, поиск и фильтры. Пустая цена сохраняется как неизвестная. История, планы и займ читаются из той же PostgreSQL, что использует бот. Для текущего личного объёма записи загружаются в браузер постранично и затем фильтруются локально; для больших журналов потребуется серверная фильтрация.
