# Развёртывание на виртуальной машине Yandex Cloud

## Первая установка

Для MVP достаточно начать с Ubuntu 24.04 LTS, 2 vCPU, 2–4 ГБ памяти и SSD от 20 ГБ. Это стартовая конфигурация без локальной языковой модели; фактические требования зависят от объёма данных. Облачные ресурсы и их оплата в репозитории не настроены автоматически.

1. Создайте VM, добавьте SSH-ключ. Разрешите входящий SSH только с нужных адресов. Входящие 8000/5432 и публичный HTTP боту не нужны: он сам опрашивает Telegram.
2. Установите Docker Engine и Compose plugin по [официальной инструкции для Ubuntu](https://docs.docker.com/engine/install/ubuntu/), а также Git и Python 3. Пользователь запуска должен иметь доступ к Docker; такой доступ даёт административные полномочия на VM.
3. Клонируйте репозиторий, выполните `scripts/configure.py` и запуск из README. Не переносите токен через аргументы команд, историю shell или сообщения.
4. Проверьте `docker compose ps` и ответ `/health`. Если переносите историю, сначала выполните импорт из README: даже удалённые тестовые записи означают, что учёт уже начат, поэтому проверять ввод нужно после импорта.
5. Создайте тестовую оплату через бота, проверьте её в сводке и удалите через карточку. Сделайте резервную копию и проверьте восстановление. Затем запишите реальный расход и план с частичной оплатой.

PostgreSQL хранит данные в именованном Docker volume. `docker compose down` сохраняет данные; **`docker compose down -v` удаляет их**. API слушает только loopback VM. Домен и сертификат для Telegram long polling не требуются.

Доступ к API с локального компьютера при необходимости — через SSH-туннель:

```bash
ssh -L 8000:127.0.0.1:8000 USER@VM_ADDRESS
```

API использует служебный Bearer-токен и заголовок `X-Telegram-User-Id`. Это доверие между сервисами, а не пользовательская веб-авторизация: владелец служебного токена может действовать от любого разрешённого ID. Не публикуйте API в интернет и не встраивайте токен в браузерный клиент. `/openapi.json` тоже требует Bearer-токен.

## Резервные копии

```bash
bash scripts/backup.sh
bash scripts/verify-backup.sh backups/flat-ДАТА.dump
```

Первый скрипт создаёт приватный архив PostgreSQL, второй восстанавливает его **в новую временную базу**, читает версию схемы и таблицы, затем удаляет только эту временную базу. Проверка не перезаписывает рабочую БД. Скрипты предполагают имена базы и пользователя `flat` из Compose.

Настройте ежедневное выполнение `backup.sh` (cron/systemd timer) и копирование архивов за пределы VM, например в приватный Yandex Object Storage с шифрованием и политикой хранения. **Автоматическое расписание, S3-выгрузка, срок хранения и оповещения пока не настроены.** Архив на том же диске не защищает от потери VM. Секрет `.env` храните отдельно в защищённом хранилище; DB-архив его не содержит.

Для аварийного восстановления создайте новую установку с пустой базой, запустите только `db`, затем восстановите архив до запуска миграций/API. Не выполняйте это в существующей рабочей базе:

```bash
docker compose up -d db
# Дождитесь healthy в docker compose ps.
docker compose exec -T db pg_restore -U flat -d flat \
  --exit-on-error --no-owner < /secure/path/flat.dump
docker compose --profile bot up --build -d
```

Восстанавливайте сначала на той версии кода, которая соответствует архиву. При новой версии приложения запускаются последующие миграции. Для смены Telegram-бота учтите, что сохранённый курсор и ключи повторных сообщений относятся к прежнему боту; MVP рассчитан на один неизменный бот на установку, такая смена требует отдельной миграции.

## Обновление

Сначала резервная копия и её проверка. Затем `git pull --ff-only` и `docker compose --profile bot up --build -d`. Миграции запускаются перед API. Для отката к старому коду заранее проверьте совместимость его схемы; возврат коммита сам по себе не откатывает базу. Сохраните используемый commit ID рядом с копией.

Для диагностики используйте `docker compose ps` и `docker compose logs --tail=100 api bot migrate`. Не публикуйте `.env`, вывод `docker compose config` или инспекцию окружения контейнеров: они могут содержать секреты. Не удаляйте webhook старого бота без запланированного переключения. Не запускайте два polling-процесса с одним Telegram-токеном.

## Границы текущей проверки

Локально проверены расчёты, диалоги через API, импорт, миграции PostgreSQL 17 и восстановление архива. Реальная переписка с Telegram и облачная VM требуют отдельной проверки после подключения токена и сервера. Автоматическая сборка контейнеров описана в GitHub Actions; актуальный статус смотрите во вкладке Actions репозитория.

## Установка, если Docker Hub недоступен

Для Linux x86_64 готовые образы собираются в GitHub Actions и публикуются в [Releases](https://github.com/im-igor/flat-expense/releases). Комплект содержит приложение и PostgreSQL. Перед публикацией проверяются загрузка архива, запуск API без сборки/скачивания образов и восстановление резервной копии. Этот способ требует доступа VM к GitHub и его хранилищу файлов; для работы бота нужен доступ к Telegram.

После успешного завершения workflow `offline bundle` для текущей версии, из папки проекта:

```bash
git pull --ff-only
bash scripts/start-offline.sh
```

Скрипт проверит архитектуру, наличие `.env`, скачает архив для текущего коммита, проверит SHA-256, загрузит образы и запустит Compose с `--no-build --pull never`. Новые пароли не создаются, существующие настройки и volume базы сохраняются. Если `.env` ещё нет, сначала запустите `scripts/configure.py` из README. Не заменяйте команду запуска на `--build`: она снова потребует доступа к исходным реестрам.

Нужны свободное место для архива и образов (рекомендуется минимум 3 ГБ) и команды `curl`, `git`, `sha256sum`, Docker Compose. Временный архив удаляется при завершении скрипта. При ошибке 404 убедитесь, что workflow `offline bundle` именно для вашего коммита завершился успешно. Готовый комплект не исправляет сетевой доступ VM; при проблемах с GitHub или Telegram потребуется отдельная сетевая диагностика. Для другой архитектуры скрипт остановится до изменений.
