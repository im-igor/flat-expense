# Устройство первой версии

Python 3.13+, FastAPI, aiogram, SQLAlchemy, Alembic, PostgreSQL 17. Docker Compose запускает базу, одноразовые миграции, API и опционально Telegram polling-процесс.

## Данные

- `categories`: два уровня, отдельный словарь владельца. Подкатегории выбираются после родительской категории.
- `plans`: независимая будущая покупка/этап, ожидаемая и согласованная полная стоимость, месяц расхода, примечание и архивный статус.
- `expenses`: независимая фактическая оплата с датой, суммой и категорией. Новая
  оплата из Telegram помечается для разбора в веб-интерфейсе; её можно оставить
  самостоятельной или зачесть в план.
- `audit`: история создания, исправлений, удаления/восстановления и исходные атрибуты импорта.
- `documents`: файл подтверждения или справочный файл до 20 МБ, его имя, MIME-тип,
  размер, SHA-256, подпись и источник. Содержимое хранится в `BYTEA` PostgreSQL,
  а не в отдельном объектном хранилище. Документ имеет одну прямую привязку к
  расходу либо плану; присланный боту файл может временно быть неразобранным.
- `drafts`: незавершённый диалог на пользователя.
- `requests`: уникальный ключ запроса, отпечаток содержания и ответ для повторной доставки.
- `bot_cursor`: подтверждённая позиция одного Telegram consumer.
- `import_batches`: контрольная сумма файла и результат первоначального импорта.
- `loan_periods`: 121 строка графика займа A–K; L–N рассчитываются сервером по той же формуле, что в исходной книге.
- `loan_import_batches`: контрольная сумма отдельно импортированного графика займа.

Деньги хранятся в целых копейках; API возвращает суммы строками с двумя знаками. Между планами и оплатами нет технических связей: после оплаты план корректируется или удаляется вручную. При зачёте Telegram-оплаты в план исходная строка удаляется, а сумма, более поздняя дата оплаты и непустое примечание переносятся в план одной транзакцией. Удаление обычной оплаты логическое, план можно архивировать или удалить. Проверка версии и блокировки PostgreSQL защищают от перезаписи устаревшей карточки. Каждая запись проверяется на принадлежность владельцу. Данные разных разрешённых Telegram ID разделены. Взносы займа не добавляются в `expenses`, поэтому контроль исходных 35 оплат остаётся точным; месячная аналитика объединяет оба источника по дате платежа.

## Доставка и сохранение

Бот передаёт Telegram update в API. Изменения и сохранённый ответ фиксируются одной транзакцией с ключом `(owner, update_id)`. Затем бот отправляет ответ человеку и подтверждает курсор. Повторная доставка возвращает сохранённый ответ, а не создаёт вторую оплату. При падении между отправкой ответа и подтверждением курсора **ответ может повториться**, финансовая запись — нет. Разные новые сообщения с одинаковой суммой считаются разными действиями.

Кнопки текущего ввода используют одноразовую версию черновика; устаревшее подтверждение не создаёт повторную запись. API-запросы создания/изменения расходов и планов требуют `Idempotency-Key`. Повтор ключа с другим содержимым возвращает конфликт. Создание категорий повторяемо по владельцу, имени и родителю.

Telegram подтверждает приём пользовательского ввода отдельно от проверки API. При недоступности API бот повторяет доставку. Это одна последовательная очередь, без брокера. Необходимо следить за доступностью: Telegram не хранит ожидающие обновления бесконечно. Работает один экземпляр бота. Пользовательский текст нигде не исполняется.

## Последующие этапы

1. Проверить живой сценарий на VM и наладить ежедневные внешние резервные копии.
2. Расширять размеченный набор проверки локальной ИИ-категоризации. Быстрый ввод и предложение категории реализованы отдельным адаптером Ollama; модель не получает доступ к SQL/секретам.
3. OCR и разбор документов. Текст документов — данные, а не инструкции.
4. Развить уже доступный веб-интерфейс: HTTPS, серверная фильтрация больших журналов и экспорт; при необходимости DataLens через отдельного read-only пользователя.
5. Плановые этапы частичных оплат и отдельные отчёты об отклонении от бюджета.

Ни один из будущих этапов не считается включённым в текущую версию.

## Веб-интерфейс

Статические HTML/CSS/JS включены в образ приложения, внешних CDN и отдельного Node-контейнера нет. Интерфейс использует существующие доменные операции `/v1`, включая версии записей и ключи повторной доставки. Веб-сессия привязана к одному настроенному владельцу, не может выбрать чужой ID и не даёт доступ к служебным Telegram-маршрутам. Для прямого HTTP-доступа используется отдельный пароль: сервер хранит только scrypt-хеш и ограничивает частые неудачные попытки входа.
