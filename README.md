# Flat Expense

Личный учёт расходов на квартиру через веб-интерфейс и Telegram: отдельные оплаты, будущие покупки и прогноз по месяцам. Первая версия считает только расходы в рублях.

## Что работает

- Веб-интерфейс: обзор по месяцам, единый журнал расходов и планов, график займа, категории, поиск и исправление записей; прямой HTTP-вход защищается отдельным паролем.

- Пошаговый ввод расхода с подтверждением: самостоятельный расход создаёт отдельную завершённую строку с одинаковой плановой и оплаченной суммой. Новые категории обоих уровней можно создать прямо в карточке.
- Быстрый ввод в Telegram одной фразой: бот разбирает сумму и дату, а локальный ИИ предлагает категорию и до трёх подходящих активных планов. Выбранный план обновляется в своей строке: сумма оплаты накапливается, а новая строка не создаётся. При неполной оплате можно оставить план открытым или финализировать его. Карточку можно исправить до подтверждения.
- План покупки: ожидаемая стоимость, фактическая согласованная цена и месяц расхода. Цена и месяц могут быть неизвестны.
- Самостоятельные расходы — отдельные завершённые строки; оплата выбранного плана остаётся в его строке без создания дубликата.
- Исправление записей, удаление с восстановлением, архив планов.
- Добавление, переименование, удаление и массовая замена категорий в существующих записях.
- Месячные сводки и прогноз до августа 2027 года: факт и план показываются с займом и без него, столбики разделены на оплаченные и запланированные суммы.
- Перенос исходного журнала Excel или подготовленной книги с архивами оплат и плана.
- График займа A–N на 121 период, обновление ключевой ставки с сайта Банка России и включение итогового взноса N в расходы по дате платежа.
- PostgreSQL, миграции, Docker Compose, скрипты резервного копирования и проверки восстановления.

Для ИИ нужен локальный Ollama, профиль Compose `ai` и `EXPENSE_AI_ENABLED=true`; настройка описана в [инструкции](docs/deployment.md#локальный-ии-для-telegram). Текст расходов не отправляется во внешние ИИ API. PDF/фото, S3 и DataLens — следующие этапы; вложения пока не сохраняются и не распознаются.

Например, отправьте боту `Вчера заплатил мастеру за штукатурку 3 731,15 рублей` или `/expense Купил диван за 50000 рублей`. Бот покажет черновик и предложит подтвердить, изменить поля либо отменить. Если сумма или категория неизвестна, он спросит их отдельно. Каждую оплату отправляйте отдельным сообщением. При недоступности ИИ работает пошаговая команда `/expense`.

## Как считаются расходы

| Поле | Значение |
| --- | --- |
| Плановая стоимость | Предварительная оценка всей покупки |
| Фактическая цена | Полная цена по договорённости/счёту, а не сумма последней оплаты |
| Фактическая оплата по плану | Накопленная сумма в той же строке плана; хранится последняя дата оплаты |
| Будущий расход | Неоплаченный остаток открытого плана |
| Известный итог месяца | Фактические оплаты + остатки открытых планов, назначенные на этот месяц |
| Взнос по займу | Столбец N графика: платёж J + налог на материальную выгоду M |

Нулевая цена — известный ноль; пустая цена — неизвестна и в итог не включается. Платежи относятся к своим датам. Каждый план относится к одному месяцу: чтобы спланировать несколько будущих этапов, создайте отдельные планы по этапам.

Например: двери оценены в 250 000 ₽, согласованная цена 280 000 ₽ и запланированы на июнь. Аванс 100 000 ₽ вносится в ту же строку плана в мае: там будет видно 100 000 ₽ оплачено и 180 000 ₽ осталось. Если дальнейших оплат не будет, план можно финализировать с фактической суммой 100 000 ₽.

Планы без даты показаны отдельно. Просроченный план сохраняет исходный месяц и отмечается в сводке этого месяца: его нужно явно перенести. `/forecast` по умолчанию начинается с текущего месяца; для просмотра старых планов задайте более раннее начало, например `/forecast 2026-01`. Финализация сохраняет план и фактически оплаченную сумму, но исключает остаток из прогноза. Время по умолчанию — Москва.

## Быстрый запуск

Нужны Docker Engine с Compose v2, Python 3 для настройки и отдельный Telegram-бот, созданный через @BotFather. Используйте числовой ID своего Telegram-аккаунта, а не ID бота или имя пользователя.

```bash
git clone https://github.com/im-igor/flat-expense.git
cd flat-expense
python3 scripts/configure.py --telegram-user-id 123456789 --with-bot
docker compose --profile bot up --build -d
curl --fail http://127.0.0.1:8000/health
```

Замените `123456789` своим ID. Токен вводится скрыто в терминале. Скрипт создаёт `.env` с правами `0600` и случайными паролями; существующий файл не перезаписывает. Не отправляйте `.env` или токен в чат/Git. Для запуска без Telegram опустите `--with-bot` и используйте `docker compose up --build -d api`.

Откройте бота и отправьте `/start`. Доступ разрешён только ID из `ALLOWED_TELEGRAM_USER_IDS`, только в личной переписке. Несколько ID можно перечислить через запятую; у каждого свой учёт, общий семейный бюджет в этой версии не реализован.

Если у бота уже есть webhook, запуск остановится, не изменяя прежнее подключение. Для параллельной работы со старым ботом создайте нового. Запускайте только один экземпляр нового бота.

## Веб-интерфейс

Для работы без Telegram можно открыть интерфейс через SSH-туннель или включить прямой HTTP-доступ с отдельным паролем. Подробные команды и границы доступа — в [инструкции](docs/deployment.md#веб-интерфейс). Служебный токен в браузер вводить не нужно.

## Команды

| Команда | Действие |
| --- | --- |
| `/expense` | Записать самостоятельную фактическую оплату |
| `/plan` | Добавить будущую покупку |
| `/expenses`, `/plans` | Списки с карточками и кнопками исправления |
| `/month 2027-06` | Сводка за месяц; без аргумента — текущий |
| `/forecast` | Прогноз до августа 2027 года |
| `/undated` | Открытые планы без месяца |
| `/deleted`, `/archive` | Восстановление расходов и планов |
| `/categories` | Справочник категорий |
| `/cancel` | Отменить текущий ввод |

Вводимая дата расхода — дата конкретного платежа. Черновики сохраняются при перезапуске. Новая команда `/expense` или `/plan` заменяет незавершённый ввод.

## Перенос Excel

Поддерживаются два формата:

1. Исходная книга с листом `Расходы`, заголовками `Дата`, `Сумма`, `Категория1`, `Категория2`, `Описание расхода`, затем примечание. Переносятся только оплаты.
2. Подготовленная книга с листами `Архив плана` и `Архив связей расходов`: переносятся независимые планы и оплаты. Прежние коды используются только для проверки контрольных сумм во время импорта и в базу не записываются. Эти листы должны содержать актуальные исходные значения; изменения только в других листах не импортируются.

Данные после первоначального переноса нужно вести в приложении. Импорт другой версии книги не является синхронизацией и блокируется, чтобы не задвоить записи. График займа импортируется отдельной командой и хранится отдельно от контрольных 35 исходных оплат.

Начальный импорт разрешён только в пустой учёт. Сначала выполните проверку, затем тот же вызов без `--dry-run`. Исходный файл не изменяется. Пример для Linux/macOS, после запуска базы:

```bash
mkdir -p imports
# Скопируйте выбранную книгу в imports/source.xlsx.
docker compose run --rm --user "$(id -u):$(id -g)" \
  -v "$(pwd)/imports:/imports:ro" migrate \
  python -m flat_expense.cli import-xlsx /imports/source.xlsx \
  --owner 123456789 --dry-run
```

В выводе будут количество оплат, их сумма и количество планов. `--dry-run` откатывает всю транзакцию. При несовпадении контрольных сумм архивов импорт отменяется. Повтор того же файла после успешного импорта возвращает прежний результат без повторной записи. Исторические сводные карточки со статусом `Оплачено`, а также карточки без полной цены, состоящие только из уже сделанных платежей, не создаются: все 35 исходных оплат сохраняются самостоятельными фактическими расходами без связей с планами. Категории из файла сохраняются; `Мтериалы` и `Материалы` нормализуются в `Черновые материалы`, а `Капремонт` — в `Кап ремонт`. Исходные значения остаются в журнале изменений. Рабочие книги и каталог `imports` исключены из Git.

После основного импорта загрузите из той же книги график займа, сверьте 35 оплат и примените подготовленный будущий план:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" \
  -v "$(pwd)/imports:/imports:ro" migrate \
  python -m flat_expense.cli import-loan-xlsx /imports/source.xlsx \
  --owner 123456789 --dry-run

# Повторите импорт займа без --dry-run, затем:
docker compose run --rm --user "$(id -u):$(id -g)" \
  -v "$(pwd)/imports:/imports:ro" migrate \
  python -m flat_expense.cli verify-xlsx /imports/source.xlsx --owner 123456789

docker compose run --rm migrate \
  python -m flat_expense.cli reconcile-future-plan --owner 123456789 --dry-run
# Проверьте результат и повторите последнюю команду без --dry-run.
```

Сверка должна показать 35 строк на 1 767 607,11 ₽ без пропусков и лишних записей. Планировщик не создаёт карточки завершённых этапов 1–2, проверяет точные суммы оставшихся этапов Neat и оценивает материалы каждого будущего этапа в 60% стоимости его работ. Для опционального этапа с нулевой стоимостью материалов сохраняется 0 ₽ и напоминание уточнить сумму. После сверки получается 88 реальных будущих планов. Из 40 покупок 32 позиции техники получают категорию `Техника` с подкатегорией помещения из исходного плана, ориентир верхнего ценового сегмента и примечание о необходимости уточнить модель и поставщика. Все 40 покупок распределяются по четыре позиции на месяц с ноября 2026 по август 2027. Оценки техники — резерв бюджета, а не коммерческие предложения. Любой план можно удалить из веб-интерфейса; фактические оплаты при этом не изменяются.

## Проверки разработки

```bash
uv sync --frozen
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

Без `TEST_DATABASE_URL` тесты используют SQLite. Для проверки конкуренции нужен PostgreSQL и **отдельная одноразовая база с именем, оканчивающимся на `_test`**: тесты удаляют таблицы этой базы. Никогда не направляйте тесты в рабочую БД. GitHub Actions запускает тесты на PostgreSQL 17, проверяет миграции, собирает контейнеры, проверяет API и восстановление резервной копии.

Подробнее: [развёртывание и эксплуатация](docs/deployment.md), [устройство и следующие этапы](docs/architecture.md).

Для обычного обновления только кода на уже работающей VM используйте `bash scripts/start-fast.sh`. Оно собирает небольшой слой поверх установленного образа без обращения к Docker Hub, GHCR или GitHub. Если изменились `pyproject.toml`, `uv.lock` или основной `Dockerfile`, скрипт безопасно остановится и попросит полный `scripts/start-offline.sh`.
